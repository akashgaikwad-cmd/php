Server Hardening Handbook

Keeping a PHP server out of attackers' hands

A layered checklist for PHP teams: fix the code, lock down the runtime, harden the web server, and watch the host. Most breaches exploit one weak layer, so close them all.

Critical High value Baseline hygiene
01

Fix the code first

Most real attacks start in application code, not the OS. This layer matters most.

  • Use prepared statementsSQL injection
    Bind every parameter with PDO or mysqli. Never concatenate user input into a query string.
  • Never feed input to shell or evalRCE
    Keep user data out of system(), exec(), shell_exec(), eval(), and dynamic include/require paths. This is how a bug becomes a shell.
  • Escape all outputXSS
    Wrap user data printed to HTML in htmlspecialchars(). Set a Content-Security-Policy header as a second line of defense.
  • Validate and whitelist inputInput
    Check types, lengths, and allowed values on everything from $_GET, $_POST, $_COOKIE, and headers. Reject rather than clean where you can.
  • Lock down file uploadsWeb shell
    Store uploads outside the web root, rename them, verify real content type, and never let a .php file land in an executable directory.
  • Protect sessions and CSRFAuth
    Regenerate session IDs on login, hash passwords with password_hash(), and require a CSRF token on every state-changing form.
02

Harden the PHP runtime

A few php.ini settings contain the damage if something does slip through.

php.ini
; hide version + errors from the world
expose_php = Off
display_errors = Off
log_errors = On

; block remote code inclusion
allow_url_fopen = Off
allow_url_include = Off

; disarm shell functions a web shell needs
disable_functions = exec,passthru,shell_exec,system,proc_open,popen

; fence PHP into the app directory
open_basedir = /var/www/yourapp

; harden session cookies
session.cookie_httponly = 1
session.cookie_secure   = 1
session.cookie_samesite = Strict
03

Patch relentlessly

A huge share of PHP compromises target old, unpatched versions and dependencies.

  • Run a supported PHP versionEOL risk
    Stay on an actively supported branch (PHP 8.3+) and apply security releases promptly. End-of-life versions get no fixes.
  • Audit your dependenciesSupply chain
    Update framework, Composer packages, and any CMS or plugins regularly. Run composer audit to flag known-vulnerable packages.
shell
# flag vulnerable Composer packages
composer audit

# update within your version constraints
composer update --with-dependencies
04

Guard the perimeter

The web server and network in front of PHP block most automated attacks before they reach your code.

  • Put a WAF in frontPerimeter
    Use Cloudflare, or ModSecurity with the OWASP Core Rule Set, to filter common injection and scanning traffic.
  • HTTPS everywhereTransport
    Terminate TLS, redirect HTTP, and send an HSTS header so browsers refuse to downgrade.
  • Deny PHP execution in upload and asset pathsWeb shell
    Configure the web server so directories like /uploads can never run a PHP file, even if one is planted there.
  • Rate-limit and lock down adminBrute force
    Throttle login endpoints, restrict admin panels by IP or VPN, and add fail2ban for repeated failures.
05

Lock down the host

If an attacker lands, the OS layer decides how far they can move.

  • Least-privilege file permissionsBlast radius
    Web files owned by a non-PHP user, the PHP worker read-only where possible, and nothing world-writable. Keep config and secrets out of the web root.
  • Firewall and minimal surfaceExposure
    Open only ports 80/443 (and SSH from trusted IPs). Disable unused services and remove default sample apps.
  • Harden SSHAccess
    Key-based auth only, no root login, and a non-standard flow behind fail2ban.
06

Watch and recover

You cannot stop everything, so plan to detect and bounce back fast.

  • Centralized logging and alertsDetection
    Ship access, error, and auth logs off the box. Alert on new PHP files in the web root and spikes in 500s or outbound traffic.
  • Tested, offline backupsRecovery
    Keep versioned backups an attacker cannot reach from the server, and actually test a restore. This is your answer to ransomware and defacement.
  • File integrity monitoringDetection
    Track changes to core files so a dropped web shell or modified page triggers an alert.
07

Quick checklist

Tick these off on your own server. Progress is saved in your browser.

This is a hardening guide, not a guarantee. Security is ongoing: review it as your stack and the threat landscape change. If you suspect an active breach, isolate the server, preserve logs, and rotate all credentials before cleaning up.
